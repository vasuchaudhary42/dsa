How sliding window really works

  
Ten strategies, one idea: a range [l, r] that only ever moves right, carrying a summary of its contents that can be updated in O(1) when an element enters or leaves.

  

    
From brute force to a window

    
A question about “the best subarray” or “how many subarrays” has n(n + 1)/2 candidates. Brute force checks each one, often re-scanning its contents: O(n²) or O(n³). A window keeps the contents summarised (a sum, a count map, a deque) and moves its two edges forward. Each edge moves at most n times, so the whole scan is O(n), even though there is a while loop inside the for loop.

    
The property that makes it legal: monotonicity

    
Think of every subarray ending at r. For conditions like “at most k distinct”, “no repeats”, “sum ≤ x with non-negative values” or “at most k changes”, validity is monotone: if [l, r] is valid, every shorter window [l′, r] with l′ ≥ l is valid too; if [l, r] is invalid, every longer one is invalid too. So the valid starts for each r form a suffix [L(r), r], and L(r) never decreases as r grows. That is the entire reason l never moves back. When a condition is not monotone, for example a sum with negative numbers or “exactly k”, a single window is the wrong tool.

Why it is O(n) even with a while loop inside
r increases n times. l only increases, and never passes r + 1, so it increases at most n times across the whole run. The while loop’s body therefore runs at most n times in total, not n times per r. Total work: O(n) steps of O(1) each, as long as adding and removing an element from the window’s state is O(1).

  
What the window can remember in O(1)
A sum or product (positive values), counts in a Map or a 26-length array, the number of distinct values (map.size, with zero counts deleted), the number of characters still missing, the count of the most frequent value. A maximum or minimum needs a monotonic deque, because removing the current maximum would otherwise cost O(k).
